## 实现

- `ImageCodec.py`：PNG 完整解码/CRC、64 MiB/1600 万像素边界、MV/MZ 头与首 16 字节 XOR、TTF/OTF cmap 缺字校验、框内排版、多行溢出拒绝、RGBA 叠字、本地 Tesseract TSV。
- `ImageService.py`：源 hash 校验、只读预览/OCR、候选私有保存；明确确认区域后才创建 `image-text` 单元。区域 ID、图片设置和单元同事务提交；原生文本重新提取保留图片单元。
- 译文沿用 TranslationCommitter/CAS/人工锁。干净底图和字体捕获到项目，底图框外任意 RGBA 像素变化会拒绝。
- 渲染生成私有候选，操作员核对 PNG 后以候选 SHA-256 批准。输入摘要绑定区域、源图、底图、字体、译文及 revision；任一变化需要重新批准。构建只读取批准的候选，沿用原相对路径、尺寸和加密扩展。
- Qt“图片文字…”提供选图、OCR、区域 JSON 校正、底图/字体、预览批准。当前框编辑是数值表单，不提供拖拽框或背景修复画笔。CLI 同样可用。

## 独立证据

- Codex 编写正反例：普通/两种加密 PNG 往返；尺寸和框外 alpha 不变；缺字、溢出、重叠、越界、bool 字号、IDAT CRC 拒绝；确认 hash 和事务版本；未批准构建拒绝；批准构建后源文件不变；更改译文后批准失效。
- OCR 进程测试确认 argv/shell=False、stdin PNG、最小环境不带 API key/代理；超时和越界 TSV 拒绝。
- Qt 实际窗口流程测试包含候选图加载、区域确认、译文提交、底图/字体捕获、预览生成和批准。合成字体只用于测试。
- 本机安装 Tesseract `5.4.0.20240606`，日语+英语。系统字体生成的 `日本語のテスト` 图片识别精确匹配；这只证明该样例，不代表普遍 OCR 准确率。
- 当前游戏 5315 个 MZ 加密 PNG。标题 `Command_0` 126×77 解码、OCR 得到一个 START，置信度约 95.87，另一个状态漏识别；候选没有自动创建单元。人工校正双状态区域后，三个标题资源生成“开始/继续/设置”候选，Codex 目视修正了分隔行残留，再批准。
- 实际消费者 `MOG_TitleCommands.js:668–702` 按 `Command_<index>` 载入，图高除二取状态帧。原尺寸含奇数高度，测试保持原尺寸并将两个文本完整置于对应帧内，不修改资源引用。
- 私有原图、预览、OCR 文本、测试副本与字体不随仓库或便携包发布。最终游戏运行效果仍需按具体资源逐张验收。
