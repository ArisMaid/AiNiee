# 任务控制与恢复约定

扫描、提取、校验、构建和游戏模型批次使用持久化任务状态。UI 提供当前扫描/提取/校验/构建
任务的暂停、继续、取消；CLI 可以通过 job_id 控制运行中的模型批次。

```text
RUNNING -> PAUSE_REQUESTED -> PAUSED -> RUNNING
RUNNING / PAUSE_REQUESTED / PAUSED -> CANCEL_REQUESTED -> CANCELLED
RUNNING -> COMMITTING -> COMPLETED / FAILED
异常退出的活动任务 -> INTERRUPTED
```

取消在下一个安全检查点生效，网络请求已经发出时等待响应返回。迟到响应保留在
私有任务记录中，不提交译文。暂停等待不持有 SQLite 事务；另一个连接可以记录控制
请求。扫描、提取、构建和外部候选执行方保留工程写锁，避免同时修改同一工程；模型
等待期间只持任务租约，人工编辑仍可提交，结果返回时重新检查修订及人工锁定。

COMMITTING 是最终发布边界。进入之前会再次检查控制请求；进入后拒绝新的暂停或
取消。这样不会出现“任务已取消但完整副本已经发布”的矛盾。该阶段失败仍记 FAILED。

恢复方式：

- **扫描中断**：工程标记在创建时即保留。打开工程并“恢复未完成的扫描”，会重新
  核对全部来源哈希，复用哈希一致的已捕获文件。已有捕获内容不会覆盖；变化时阻断。
- **提取中断（0.6）**：有 document journal 的任务用 GUI“恢复提取…”或
  `resume-extract --project PROJECT --job-id ID`，复核当时冻结的规则、来源与缓存，复用
  已完成 JSON/JS 结果。新数据集或损坏缓存拒绝，人工译文/锁保留；最终数据、问题及
  完成状态原子提交。旧版无 journal 的任务仍重新提取。见 EXTRACTION_RECOVERY_EVIDENCE.md。
- **模型中断**：从 SQLite 已接受单元继续，重新准备待译批次，旧响应仍受版本比较约束。
- **迁移中断（0.7）**：迁移窗口“恢复未完成的迁移…”或
  `resume-migration --project PROJECT --job-id ID`。新尝试核对原对账、双侧版本和原子
  accepted 提案，复用连续已提交前缀。后来的人工改稿/锁保持；未提交条目重新完整
  校验，任一变更要求新对账。最后 registry 和 COMPLETED 原子发布，失败报告保留。
  没有冻结输入的旧任务需要新对账。见 MIGRATION_RECOVERY_EVIDENCE.md。
- **校验中断（0.5）**：GUI“恢复校验…”或 `resume-validation --project PROJECT --job-id ID`
  复核冻结输入与有序检查点后继续。当前工程有新编辑时要求重新校验；损坏证据保留。
  新 attempt 不改写旧的取消/失败记录。只读检查不产生任务或文件，详见
  VALIDATION_RECOVERY_EVIDENCE.md。
- **构建中断（0.1.1-dev）**：有 resume.sqlite3 的构建可通过 GUI“恢复构建…”或
  `resume-build --project PROJECT --build-id ID` 继续。每次生成新 attempt_id，保持冻结
  译文与输入 revision，当前工程的新编辑不会被覆盖。逐文件复核来源、实际输出 SHA
  和冻结写入计划；合法文件复用，损坏文件单个保留后重写，未知文件阻止发布。完成后
  再核对完整来源与捕获输入。旧版没有 journal 的失败构建需新建。
- **发布后进程退出**：若完整副本已经改名发布，恢复不会覆盖它；重新核对完整清单、
  来源、冻结写入计划、字体/采集资源后登记原成品。缺项、额外文件或越界差异均拒绝。
- **保留边界**：通过同一文件系统的单文件 rename 将损坏文件保留在项目 builds 下；
  输出与项目跨盘且需要保留损坏文件时明确拒绝，不隐含执行复制后删除。
- **进程消失**：recover 在取得工程锁后把活动任务（含 COMMITTING）标记 INTERRUPTED。
  它不会恢复执行线程，也不会自动宣布保留的副本通过运行验收。扫描、提取、构建和
  模型请求、迁移及校验均持有 OS 任务租约；仍活跃的租约会被跳过。遗留 PAUSED 也会被识别，
  进程已消失的暂停任务不能直接标为继续执行。

测试覆盖了两连接暂停等待和恢复、暂停后取消、扫描恢复、取消构建不发布、提交阶段
拒绝取消及模型迟到响应不写入。构建另有真实子进程 os._exit 后恢复、取消后明确恢复、
来源/冻结输入变化拒绝、检查点 hash 被改仍不能绕过写入计划、采集安装后失败恢复和
发布后登记测试。当前游戏完成取消→注入失败→再恢复，复用 100 个文件，9570 个输出
文件验证通过，17 个已接受译文保持不变。迁移另有实际子进程提交前后退出、原子发布
回滚及当前游戏数据库图 8+19 条恢复记录；完整进程树超时控制另行核验。
锁、失败文件和产物均保留，无目录清理。

## 0.14 基础恢复、并发打开与租约

恢复先取得工程写锁，再读取活动任务的五列摘要（job_id、operation、run_state、stage、
checkpoint）。它不枚举历史 payload/result，也不解码活动任务的大结果。对每个候选，
取得其 OS 任务租约后在 BEGIN IMMEDIATE 事务中条件更新：只有仍为 RUNNING、
PAUSE_REQUESTED、PAUSED、CANCEL_REQUESTED、COMMITTING 才改为 INTERRUPTED。
stage、checkpoint、payload、结构化错误和原响应保留，数据集及内容版本不增加。

任务可能在枚举后正常结束；此时条件更新返回未改变，不会执行终态到 INTERRUPTED
的非法转换。租约仍忙但数据库已是终态时，恢复也不再将其报告为活动任务。OS 锁随
进程句柄释放，磁盘上的锁文件保留；没有基于文件年龄、墙钟或 PID 的租约抢占机制。

源码证据包括受保护的恢复竞争用例，以及真实 Windows Job Object 进程树：模型
等待/暂停时退出、实际模型执行方在枚举和租约探测之间失败、两个 Qt 页面并发读取、
人工修改及锁定后迟到模型结果拒绝。共新增 17 项专项测试；请求器为合成实现，没有
使用真实模型接口。旧 0.13 实际 EXE 在 SQLite 写事务屏障中复现终态竞争并 exit 1，
保留其现场用于新 EXE 对照，屏障本身是合成故障时序。

当前游戏数据库通过 SQLite backup 建立一致副本，包含 17716 单元。副本中只添加一条
明确的人工测试译文；实际 Stev 后端在新复制的 SDK 文件上设置导入等待点。两个完整
应用 GUI 进程均可读取 17716 行，第二个写操作及恢复被 PROJECT_BUSY 拒绝；结束所属
进程树后，遗留任务可标中断，旧检查点保留，新后端候选可正常完成。源游戏及主工程
没有写入。这证明工程服务及租约协调，不代表原游戏运行或全量翻译通过。

0.14 源码当前游戏图证据：work/frozen-project-leases/609eac692f3e48769f8e24a6827c5088。
新便携包结果以对应版本 DELIVERY.json 和 EXTRACTED_PACKAGE_CHECK.json 为准；
没有把 0.13 的实际 EXE 结果当作新版本验证。完整游戏 GUI 流程仍在 F01 单独跟踪。

### 构建文件短占用与持续失败

0.14 首轮完整回归出现 382 passed / 207 subtests passed、1 failed：副本地图的
os.replace 返回 WinError 5，旧目标与已写完的独立暂存均保留，两者属性为 Archive。
该现场保留在 work/acceptance/adapter-egvirxeq-output；没有据此推测具体占用进程。
随后用真实 Windows 禁止 delete sharing 的读句柄稳定复现相同错误。

PathGuard.atomic_write 只为 overwrite=True 的 Windows 5/32/33 替换错误增加最多六次
尝试，五次延迟为 .03/.06/.12/.24/.48 秒，总计 .93 秒。每次使用同一份已关闭且 fsync
完成的暂存，重新核对目标及暂存的重解析点和硬链接。无覆盖写入仍保持原有拒绝语义；
无关错误直接传播。永久权限拒绝不会通过重试获得额外权限，最终仍失败并保留文件。

新增七项源码用例验证短占用释放后完成、持续占用有界失败、旧暂存保留、无关错误
立即失败、no-overwrite 不变，以及延迟期间新增目标/暂存硬链接时拒绝继续写入。
源码完整 CLI 另通过合成 MZ 工程及真实 Stev API 导入等待点，确定文件已复制后再持有
原生句柄：短占用可构建发布并 verify；持续占用的尝试 FAILED、不发布，原目标及完整
暂存保留，释放后显式新建构建可通过。证据 work/frozen-atomic-build/99ebe646a95e4a3794c9b1eace792b37。
该试验未声称旧构建可自动复用未登记的暂存；未知文件仍阻止发布，此边界由 E05 继续
跟踪。新便携 EXE 会独立运行相同场景，以版本交付回执为准。

## 0.15 已登记原子暂存的恢复协议

构建写入计划 v7 在每次输出原子写入前创建不可覆盖登记，位于对应构建记录下的
atomic-writes/UUID.json。登记包含构建 ID、尝试 ID、冻结数据库摘要、写入计划摘要、
唯一暂存名称、合法目标路径，以及预期内容摘要和长度。实际输出暂存名由同一 UUID
预分配，仍以排他模式打开。翻译、配置字体、字体别名脚本、采集脚本、HTML 和完成
标记的原子写入均接入；登记文件本身位于工程记录中，不进入发布副本。

恢复只读取严格合法的已提交登记，拒绝重复 JSON 键、错误版本、路径越界、重解析点、
硬链接、未知尝试和构建/冻结输入绑定冲突。没有通过扫描 *.staging 名称来授予权限。
已登记暂存按实际字节流计算摘要与长度，包括半写入或损坏内容；先提交不可覆盖的
atomic-recovery/UUID.json，再以单文件 rename 移入 atomic-retained/UUID.bin。
两侧须在同一文件系统，任何一步失败均保留证据，无目录清理或复制后删除。

归档证据绑定原登记的原始字节摘要和实际文件摘要。若进程在证据提交后、rename 前
退出，下次核对同一证据后继续；若在 rename 后退出，下次核对已归档文件继续，不会
再移动一次或覆盖它。存在相互矛盾的源/归档文件、摘要变化、缺失证据或归属不符时
阻断。归档保留的内容不成为文件级成功检查点，输出仍按冻结输入重新生成并接受
原有 JSON/JS/图片及完整文件集合校验，人工后续编辑和锁不被旧构建覆盖。

原 SQLite 工程格式及 BuildJournal 物理 schema 1 不改。写入计划版本升级为 v7；旧
v6 未完成任务需要明确新建构建，不对旧的未登记暂存猜测来源。已完成旧副本仍可
按清单独立 verify。完整 E05 以及全游戏运行仍按实施状态单独跟踪。

源码红灯证明：0.14 在真实 Win32 禁止 delete-sharing 句柄释放后恢复原构建，仍报
BUILD_STAGING_FILE_SET_CHANGED；保留目录 462e1007b86a4d359babb4e91d560e5d。
旧 0.14 实际 EXE 的同类 CLI 验收也复现该错误；两者均在新的合成工程中执行，没有
修改旧交付 ZIP 或既有验收现场。0.15 正反例及新 EXE 验收结果以本版回执为准。
